# AI API を叩くときに考えること — LLM を本番機能に組み込む前に確認する6つの観点

こんにちは。株式会社メドレーのジョブメドレー開発グループでエンジニアをしている◯◯です。

ジョブメドレーでは、事業所の方が作成した求人原稿を掲載前に審査しています。この審査の一部を LLM に任せ、問題がなければ即時掲載できるようにする機能を開発してきました。

LLM を使った機能開発の情報はプロンプトの書き方に偏りがちですが、実際に本番に組み込んでみると、悩む時間が長いのはむしろ「API をどう叩くか」でした。どのプラットフォームから叩くか、どのモデルを選ぶか、コストをどう抑えるか、エラーが返ってきたらどうするか。チュートリアルには出てこないのに、本番では避けて通れない論点です。

この記事では、それらの検討事項を上から順に確認できる形に整理しました。特定のプロバイダに依存しない書き方をしつつ、例示には私たちが使った Vertex AI / Gemini を使います。プロンプト設計や審査ロジックの中身には踏み込みません。

## 1. プラットフォーム選定 — どこから叩くか

最初の分岐は「モデル提供元の API を直接叩く」か「クラウドベンダー経由で叩く」かです。同じモデルでも入口が複数あります。

| | 直 API | クラウド経由 |
|---|---|---|
| 例 | OpenAI API / Anthropic Claude API / Gemini Developer API | Vertex AI / Amazon Bedrock / Azure OpenAI |
| 認証 | API キー | IAM(既存のクラウド権限管理に乗る) |
| 請求 | プロバイダと直接契約 | 既存のクラウド請求に合算 |
| 監査・統制 | プロバイダのログ機能に依存 | クラウドの監査ログ・VPC 統制が使える |
| 新機能・新モデル | 最速で提供される | 提供が遅れる・来ないことがある |

見落としやすいのは最後の行です。「同じモデルなら同じ機能が使える」とは限らず、クラウド経由は機能のサブセットになることがあります。たとえば Claude の場合、明示的なプロンプトキャッシュは直 API・Bedrock・Vertex AI のいずれでも使えますが、Batch API や一部のサーバーサイドツールは直 API 限定です[^claude-platform]。Gemini も、新機能が Developer API に先に来て Vertex AI が後追いになることがあります。

選定チェックリスト:

- 社内に既存の LLM 利用実績があるなら、まず同じ経路に乗る(認証・請求・レビューの仕組みを再利用できる)
- 使いたい機能(キャッシュ、Batch、structured output など)が、選んだ経路で提供されているか公式の対応表で確認する
- コストを機能単位で按分したいなら、リクエストにラベルを付ける手段(Vertex AI のカスタムメタデータラベルなど)があるか確認する

> 私たちの場合: 社内に GCP の利用実績と Vertex AI 経由の LLM 機能が既にあり、IAM 認証・請求統合の都合もあって Vertex AI を選びました。

## 2. モデル選定 — どのモデルで叩くか

### tier 構造と価格

主要プロバイダのモデルはどこも「フラッグシップ / バランス / 軽量」の階層構造になっています。2026年7月時点の代表例です[^pricing]。

| | フラッグシップ | バランス | 軽量 |
|---|---|---|---|
| OpenAI | GPT-5.5 ($5 / $30) | GPT-5.4 ($2.5 / $15) | GPT-5.4 mini ($0.75 / $4.5) |
| Anthropic | Claude Opus 4.8 ($5 / $25) | Claude Sonnet 4.6 ($3 / $15) | Claude Haiku 4.5 ($1 / $5) |
| Google | Gemini 3.1 Pro ($2 / $12 ※) | Gemini 3.5 Flash ($1.5 / $9) | Gemini 3.1 Flash-Lite ($0.25 / $1.5) |

(単位は $/100万トークン、入力 / 出力。※ Gemini は入力20万トークンを境に価格が上がる階段制。各社ともこの表の上にさらに高価格帯の最上位モデルがあり、ラインナップは頻繁に入れ替わるので、選定時は必ず公式の価格ページを確認してください)

<!-- 公開直前: 表のモデルが最新世代か再確認。ファクトチェック時点で Anthropic は Fable 5 ($10/$50)、OpenAI は GPT-5.6 世代が公式ページに掲載済み -->


tier を1つ下げると価格はおよそ1桁近く変わります。つまりモデル選定はコスト最適化の最大のレバーでもあります。問題は「下げても精度が保てるか」をどう判断するかです。

### 精度は適合率・再現率で語る

精度・コスト・レイテンシの3つは同時には取れないので、優先順位を決めます。このとき最初にやるべきなのは、ベンチマークスコアの比較ではなく「どちらに間違えると致命的か」の定義です。

審査のような判定タスクは混同行列で整理できます。私たちの場合、「違反のある求人を見逃して承認する」(false negative)と「問題ない求人を誤って弾く」(false positive)では意味がまったく違います。前者は法令違反の求人が掲載されるので致命的、後者は人手の二次審査で救済できます。つまり再現率を優先し、適合率は下流で補う設計です。

この定義があると、モデルの比較検証で見るべき数字が決まります。注意したいのは、単純な「一致率」は当てにならないことです。項目別の一致率が高くても、項目を束ねた最終判定では乖離が拡大します(束ねる項目が多いほど、どれか1つの不一致で全体の判定が変わるため)。また正例(違反)が少ないデータでは、一致率が高いのに再現率が壊れていることもあります。

### 検証レーンを常設する

モデルの比較検証は一度きりではありません。プロバイダのモデルには廃番(retirement)があり、その猶予は思ったより短いからです[^deprecations]。

| | 廃止通知から停止までの猶予 |
|---|---|
| OpenAI | GA モデルは最低6か月、preview は2週間程度 |
| Anthropic | 最低60日 |
| Google | preview は最低2週間(GA の固定日数は明記なし) |

preview 系のモデルを本番に据えると、2週間で切替を迫られる可能性があるということです。切替のたびにゼロから検証環境を組むのではなく、本番と同じ入力を別モデルでも処理して結果だけ蓄積する「検証レーン」を常設しておくと、切替検証がすぐ回せます。この領域には golden dataset(人手レビュー済みの評価用データセット)、LLM regression testing(モデルやプロンプトを変えるたびに固定データで再実行して基準と比較する)、offline eval といった確立した用語と手法があるので、これらで検索すると設計の参考になります。

進め方の定石は「上位モデルで作って動かしてから、下位モデルを検証する」です。逆順だと、何と比較して精度を測るのかの基準がありません。

> 私たちの場合: 本番審査と検証審査(結果を使わず蓄積のみ)の二系統を常設しています。下位モデルの検証では、本番モデルとの乖離がすべて「厳しい側」(=再現率は落ちていない)だったため採用、という判断ができました。

## 3. コスト — トークンは思ったより減らせる

LLM API の料金は「入力トークン数 × 単価 + 出力トークン数 × 単価」の従量制で、出力単価は入力の5〜6倍です。削減手段を効果が大きい順に並べます。

1. **そもそも呼ばない**。数値比較・正規表現・presence チェックで決まる判定を LLM に混ぜない。コードに降ろせば、その分のプロンプトも並列実行も丸ごと消えます。入力フォームのバリデーションで手前で弾ければ、審査自体が走りません
2. プロンプトキャッシュを使う(後述)
3. 入力を削る。structured output(決まったスキーマでの出力を API 側に保証させる機能。4章で詳述)を使うなら、JSON の書式指示はプロンプトから消せます。ID をエコーバックさせる指示なども仕様上不要なら削ります
4. 出力を削る。下流で誰も使わない生成をさせない。私たちの例では、承認時の判定理由文はどこにも表示していなかったので、非承認時だけ生成するようにしました
5. モデルを下げる。前章の検証レーンで精度を確認してから

### プロンプトキャッシュは3社3様

複数のリクエストで共通するプロンプト部分(システムプロンプトや共通ルール)は、キャッシュで大幅に安くなります。「キャッシュはクラウド経由でないと使えない」と思われがちですが、むしろ各社の直 API が一次提供元です。ただし方式がそれぞれ違います[^caching]。

| | 方式 | 制御 | 課金 |
|---|---|---|---|
| Anthropic | 明示的(cache_control でキャッシュ位置を指定) | TTL 5分 / 1時間を選択 | 書込みに1.25〜2倍のプレミアム、読出しは約0.1倍 |
| OpenAI | 完全自動(1,024トークン以上のプレフィックス) | なし | 書込み無料(新世代は1.25倍)、読出しは標準の10〜25% |
| Google | implicit(自動) + explicit(cachedContents)の併用 | explicit は TTL 指定 | explicit はキャッシュ保持にストレージ時間課金 |

どの方式でも共通する原則が1つあります。キャッシュはプロンプトの先頭からの前方一致で効くので、**安定した内容を前に、リクエストごとに変わる内容を後ろに置く**ことです。システムプロンプトの先頭に現在時刻を埋め込むだけで、以降のキャッシュがすべて無効になります。

また、explicit 方式では TTL の管理責任がアプリ側にも生じます。「キャッシュがあるはず」を前提にした実装は、TTL 切れのタイミングで挙動が変わるので、アプリ側でもキャッシュの存在を保証する(なければ作ってから使う)設計にします。

> 私たちの場合: 決定的な判定のコード降ろしと、プロンプトから不要な指示・生成を削る見直しだけで、入力トークンを大きく削減できました。

## 4. リクエストオプション — デフォルトのまま叩かない

API リクエストのオプションは、デフォルトのままだと本番で困るものがいくつかあります。

| オプション | デフォルトのまま叩くと | 推奨 |
|---|---|---|
| ロール(system / user) | ユーザー由来テキストを system に混ぜると、プロンプトインジェクションの入口になる | 指示は system、ユーザー由来テキストは user に隔離 |
| structured output | 出力の JSON パース失敗をアプリ側で処理し続けることになる | スキーマ指定で書式を API 側に保証させる |
| 安全フィルタ | ドメイン特有の語彙が誤ってブロックされることがある | 自ドメインの入力で挙動を確認し、明示設定する |
| temperature | 判定タスクでも出力が揺れる | 判定タスクは決定性寄りに設定(ただし後述の通り保証はない) |
| タイムアウト | SDK のデフォルト(10分程度)が長すぎて、ジョブ側のタイムアウトと不整合を起こす | 呼び出し側の想定に合わせて明示設定 |

いくつか補足します。

**ロール分離**はどのプロバイダでも一級のインジェクション対策として位置づけられています。OpenAI は Model Spec で命令の優先順位(Platform > Developer > User)を定義してモデルを訓練しており[^hierarchy]、Anthropic もロール定義とユーザー入力の分離を公式に推奨しています。審査対象の原稿のような「外部の人間が書いたテキスト」を扱うなら、正規表現でのサニタイズよりも先に、まずロールを分けます。

**structured output** は3社とも提供していますが制約が違います。OpenAI は再帰スキーマに対応する一方で数値の範囲制約が使えず、Anthropic は再帰非対応、Gemini は `propertyOrdering` を明示しないと出力順が安定しない、複雑なスキーマは 400 エラーになる、といった癖があります[^structured]。スキーマ設計の前に制約一覧を確認してください。

**安全フィルタ**は仕組み自体が3社で違います。Gemini はリクエスト単位で閾値を調整でき、OpenAI は生成 API と分離した無料の moderation API、Anthropic は閾値設定なしで拒否時に `stop_reason: "refusal"` を返す方式です。医療・介護の求人原稿には「注射」「入浴介助」「精神科」のような語が普通に登場し、Gemini のデフォルト設定では誤ブロックの可能性があるため、私たちは safety settings を明示的にオフにしました(医療系での誤発動は公式フォーラムでも報告されています[^safety])。フィルタを切る場合は、代わりの安全策(ロール分離、出力の検証)を持っているのが前提です。

**決定性**は、どの社も保証していません。OpenAI と Gemini には `seed` パラメータがありますが best-effort ですし、Anthropic に至っては新しいモデルで temperature パラメータ自体が廃止されました。「同じ入力なら同じ出力」を前提にした設計はできない、というのが次章・次々章の前提になります。

> 私たちの場合: safety settings の明示オフに加え、審査対象の原稿を user ロールに隔離してインジェクション耐性を確保しています。

## 5. エラー対応 — 429 と「200 なのに失敗」に備える

LLM API のエラーは、リトライで直るものと直らないものを分けて設計します。

| エラー | 意味 | リトライ |
|---|---|---|
| 429 | レート制限超過 | する(バックオフ付き) |
| 500 / 503 / 529 | プロバイダ側の障害・過負荷 | する(バックオフ付き) |
| 400 / 403 | リクエスト不正・権限不足 | しない(直して再送) |
| タイムアウト | 応答が返らない | 冪等なら再送 |
| 200 だが空応答・拒否 | 安全フィルタ等による拒否 | しない(後述) |

### レート制限の考え方は3社3様

429 対策の前に、レート制限の単位を知る必要があります。ここもプロバイダごとに思想が違います[^ratelimit]。

- OpenAI: リクエスト数/分とトークン数/分の複数軸。上限は累積課金額に応じて自動昇格
- Anthropic: 入力トークンと出力トークンが別々の上限を持つ(入力だけ・出力だけで 429 になりうる)。自動昇格に加えて引き上げ申請・個別交渉の窓口がある。キャッシュ読出しは入力側に計上されないため、キャッシュが実効スループット向上にも効く
- Vertex AI: 新しめのモデルは Dynamic Shared Quota(DSQ)で、固定クォータも引き上げ申請も存在しない。429 は「自分の上限超過」ではなく「共有リソースプールの瞬間的な混雑」を意味する

とくに DSQ の 429 は誤解しやすいポイントです。自分のリクエスト数を数えていても防げず、プール側の混雑で発生します。global エンドポイントを使うと複数リージョンの容量に分散されて頻度が下がります[^dsq]。

対策の定石は次の3点です。

- 並列数をクライアント側で制御する。1件の処理で複数プロンプトを並列発行する設計だと、「処理の同時多発 × プロンプト並列」の掛け算でリクエストが瞬間的に集中します。並列の上限は自分で持ちます
- 429/5xx はジッター付き指数バックオフでリトライする。`retry-after` ヘッダが返ってきたらそれに従います(Anthropic は「それより早いリトライは失敗する」と明記しています)。固定間隔の即時リトライは、混雑をさらに悪化させるアンチパターンです
- リアルタイム性が不要な処理は Batch API に逃がす。3社とも50%割引で、同期 API とは別のクォータ枠なので、レート制限そのものを回避できます[^batch]

### 200 なのに失敗、に備える

HTTP ステータスだけ見ていると、すり抜ける失敗があります。4章で見た安全フィルタの拒否がその代表例で、3社とも正常応答(200)の中に入って返ってくるからです。Anthropic は `stop_reason: "refusal"`、OpenAI は structured output の `refusal` フィールドで返します。Gemini は2パターンあり、入力段階でブロックされると candidates 自体が空に、生成段階でブロックされると content が空で `finishReason: SAFETY` になります[^refusal]。これらはリトライで直らないので、リトライ対象から外し、明示的に検出してフォールバックに回します。

### フォールバック先を最初に決める

リトライしても直らないとき、ユーザー体験をどう守るかは実装前に決めておきます。私たちは「AI 審査がエラーになったら、従来どおりの人手審査フローに静かに戻す」と決めていました。ユーザーから見ると「即時掲載されなかった」だけで、エラー画面は見せません。LLM を「失敗したら人間に返す高速化レイヤー」と位置づけると、この設計は自然に出てきます。

もう1つ、非同期処理特有の罠として「エラーにすらならず、進行中のまま止まる」ケースがあります。処理状態を管理するテーブルを持つなら、タイムアウトで状態をリセットする後始末までを設計に含めます。

> 私たちの場合: モデル更新後に 429 が頻発したことがあり、並列上限の導入とリトライ整備で収束しました。エラー時のフォールバックが決まっていたため、この間もユーザー影響はありませんでした。

## 6. 動作確認とリリース — 正解のない出力をどう検証するか

最後は「作った機能をどう確認してリリースするか」です。LLM 機能のテストには固有の難しさがあります。出力の期待値を事前に定義できず(そもそも正解を列挙できるなら LLM は要りません)、しかも前述のとおり出力は非決定的です。テスト分野ではオラクル問題と呼ばれる状況で、通常の「入力 X なら出力 Y になるはず」という assert が書けません。

この状況で使えるテスト手法が知られています[^oracle]。

- **Property-based Testing**: 個別の正解ではなく「すべての出力が満たすべき性質」を検証します。審査なら「判定は必ず承認か非承認のどちらか」「非承認なら理由が必ず付く」。前述の structured output と組み合わせると、性質の多くを API 側で保証できます
- **Metamorphic Testing**: 入力を変えたときに出力がどう変わる「べき」かの関係を検証します。審査なら「原稿の無関係な箇所(事業所名など)を変えても判定は変わらない」「違反表現を追加したら、判定は非承認側にしか動かない」。とくに後者のような方向つきの関係は、2章で定義した「間違いの非対称性」をそのままテストにできます

そして最終検証は本番トラフィックで行います。段階は3つです。

1. シャドー実行: 本番の入力で LLM を動かすが、結果は使わず蓄積だけする。既存フロー(人手審査)の結果と突き合わせられるので、2章の適合率・再現率をここで実測できます
2. 少量リリース: 対象の数%だけ結果を実際に使い、計測する
3. 段階拡大: 数字を確認しながら比率を上げる

> 私たちの場合: シャドー実行で既存の審査結果との比較を行い、ズレる箇所を特定・修正してから、1% → 段階拡大の順で本番適用しました。

## さいごに

全体を1枚のチェックリストにまとめます。

- [ ] プラットフォーム: 社内の既存経路に乗れるか。使いたい機能はその経路で提供されているか
- [ ] モデル: どちらに間違えると致命的か(適合率 vs 再現率)を先に定義したか。検証レーンはあるか
- [ ] コスト: LLM でなくていい処理を混ぜていないか。キャッシュの前方一致を意識したプロンプト配置か。使わない出力を生成させていないか
- [ ] オプション: ロール分離・structured output・安全フィルタ・タイムアウトをデフォルトのまま叩いていないか
- [ ] エラー: 429/5xx のバックオフと並列制御はあるか。「200 なのに失敗」を検出しているか。フォールバック先は決めたか
- [ ] 検証: 出力の性質と入出力の関係をテストしているか。シャドー実行で実測してから段階リリースしているか

こうして並べると、LLM API の扱いは外部 API 連携の一般論とほとんど同じです。違うのは、レスポンスが非決定的で、課金が従量で、モデルが向こうの都合で入れ替わっていくこと。この3点への備え(検証レーン、コスト設計、段階リリース)さえ仕組みにしておけば、LLM は特別扱いの要らない普通の部品として運用できます。この記事が、これから LLM を本番に組み込む方の地図になれば幸いです。
