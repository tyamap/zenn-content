本日は医療介護の求人サイト「ジョブメドレー」での LLM 機能導入に際して、調べたことや学んだことを紹介したいと思います！

# はじめに

LLM を使った機能を開発する場面は、ますます増えていると思います。

LLM の話題はプロンプトの書き方に偏りがちですが、実際にシステムへ組み込んでみると、悩む時間が長いのはむしろ「API をどう叩くか」でした。
どのプラットフォームから叩くか、どのモデルを選ぶか、実行環境はどうするか、コストをどう抑えるか、エラーが返ってきたらどうするか。
チュートリアルには出てこないのに、本番では避けて通れない論点です。

この記事では、それらの検討事項を上から順に確認できる形に整理しました。
特定のプロバイダに依存しない書き方をしつつ、例示には私たちが使った Vertex AI / Gemini を使います。
LLM API レイヤにのみ焦点を絞り、プロンプト設計や実行環境の設計、ロジックの中身には踏み込みません。

また、LLM の使いどころにはテキストの要約、自然言語からのクエリ生成、条件判定などさまざまな形がありますが、本文の例は「入力テキストが条件を満たすかを true / false で判定する機能」に統一します。
私たちが本番に組み込んだのもこのタイプです。
入出力が単純なぶん、コスト・精度・エラー対応の論点を見通しよく示せます。

# 1. プラットフォーム選定 — どこから叩くか

最初の分岐は「モデル提供元の API を直接叩く」か「クラウドベンダー経由で叩く」かです。
同じモデルでも入口が複数あります。

|          | 直 API                                                    | クラウド経由                                    |
| -------- | -------------------------------------------------------- | ----------------------------------------- |
| 例        | OpenAI API / Anthropic Claude API / Gemini Developer API | Vertex AI / Amazon Bedrock / Azure OpenAI |
| 認証       | API キー                                                   | IAM(既存のクラウド権限管理に乗る)                       |
| 請求       | プロバイダと直接契約                                               | 既存のクラウド請求に合算                              |
| 監査・統制    | プロバイダのログ機能に依存                                            | クラウドの監査ログ・VPC 統制が使える                      |
| 新機能・新モデル | 最速で提供される                                                 | 提供が遅れる・来ないことがある                           |

見落としやすいのは最後の行です。
「同じモデルなら同じ機能が使える」とは限らず、クラウド経由は機能のサブセットになることがあります。
たとえば Claude の場合、明示的なプロンプトキャッシュは直 API・Bedrock・Vertex AI のいずれでも使えますが、Batch API や一部のサーバーサイドツールは直 API 限定です。

https://platform.claude.com/docs/en/build-with-claude/claude-in-amazon-bedrock

Gemini on Vertex AI も、新機能が Developer API に先に来て Vertex AI が後追いになることがあります。

- 社内に既存の LLM 利用実績があるなら、同じ経路に乗ることを検討する。認証・請求・レビューの仕組みを再利用できる
- キャッシュや Batch、structured output など、使いたい機能が選んだ経路で提供されているか確認する
- コストを機能単位で按分したいなら、Vertex AI のカスタムメタデータラベルのような、リクエストにラベルを付ける手段があるか確認する

# 2. モデル選定 — どのモデルで叩くか

## tier 構造と価格

主要プロバイダのモデルはどこも「フラッグシップ / バランス / 軽量」の階層構造になっています。
ラインナップは頻繁に入れ替わるので、選定時は必ず公式の価格ページを確認してください。

https://platform.claude.com/docs/en/about-claude/pricing

https://developers.openai.com/api/docs/pricing

https://ai.google.dev/gemini-api/docs/pricing

tier を1つ下げると、価格はおよそ1桁近く変わります。
つまりモデル選定は、コスト最適化の最大のレバーでもあります。
問題は「下げても精度が保てるか」ですが、これは評価の話なので6章でまとめて扱います。

選定の進め方には定石があります。
「上位モデルで作って動かしてから、下位モデルを検証する」です。
逆順だと、何と比較して精度を測るのかの基準がありません。

## モデルの EOL に備える

モデル選定は一度きりでは終わりません。
プロバイダのモデルには EOL があり、その猶予は思ったより短いからです。

| | 廃止通知から停止までの猶予 |
|---|---|
| OpenAI | GA モデルは最低6か月、preview は2週間程度 |
| Anthropic | 最低60日 |
| Google | preview は最低2週間(GA の固定日数は明記なし) |

https://platform.claude.com/docs/en/about-claude/model-deprecations

https://developers.openai.com/api/docs/deprecations

https://ai.google.dev/gemini-api/docs/models

Gemini の preview の2週間前通知は、models ページに記載されています。

preview 系のモデルを本番に据えると、2週間で切替を迫られる可能性があるということです。
つまり「いま最良のモデルを選ぶ」だけでなく「切替を前提に選ぶ」必要があります。
切替の検証をすぐ回せる仕組みは、6章の検証レーンで扱います。

# 3. コスト — トークンは思ったより減らせる

LLM API の料金は「入力トークン数 × 単価 + 出力トークン数 × 単価」の従量制で、出力単価は入力の5〜6倍です。
削減手段を効果が大きい順に並べます。

1. **そもそも呼ばない**。数値比較・正規表現・presence チェックで決まる判定を LLM に混ぜない。コードに降ろせば、その分のプロンプトも並列実行も丸ごと消えます。入力フォームのバリデーションで手前で弾ければ、LLM の判定自体が走りません
2. **プロンプトキャッシュを使う**。詳しくは次の節で説明します
3. **入力を削る**。4章で詳述する structured output を使えば出力の書式は API 側が保証するので、JSON の書式指示はプロンプトから消せます。ID をエコーバックさせる指示なども仕様上不要なら削ります
4. **出力を削る**。下流で誰も使わない生成をさせない。私たちの例では、判定が true のときの理由文はどこにも表示していなかったので、false のときだけ生成するようにしました
5. **モデルを下げる**。6章の検証レーンで精度を確認してから

実際、私たちは決定的な判定のコード降ろしと、不要な指示・生成を削る見直しだけで、入力トークンを大きく削減できました。

## プロンプトキャッシュは3社3様

システムプロンプトや共通ルールのような、複数のリクエストで共通するプロンプト部分は、キャッシュで大幅に安くなります。
「キャッシュはクラウド経由でないと使えない」と思われがちですが、むしろ各社の直 API が一次提供元です。
ただし方式がそれぞれ違います。

| | 方式 | 制御 | 課金 |
|---|---|---|---|
| Anthropic | 明示的(cache_control でキャッシュ位置を指定) | TTL 5分 / 1時間を選択 | 書込みに1.25〜2倍のプレミアム、読出しは約0.1倍 |
| OpenAI | 完全自動(1,024トークン以上のプレフィックス) | なし | 書込み無料(新世代は1.25倍)、読出しは標準の10〜25% |
| Google | implicit(自動) + explicit(cachedContents)の併用 | explicit は TTL 指定 | explicit はキャッシュ保持にストレージ時間課金 |

https://platform.claude.com/docs/en/build-with-claude/prompt-caching

https://developers.openai.com/api/docs/guides/prompt-caching

https://ai.google.dev/gemini-api/docs/generate-content/caching

Gemini の explicit caching は、generateContent 版のページに記載されています。

どの方式でも共通する原則が1つあります。
キャッシュはプロンプトの先頭からの前方一致で効くので、**安定した内容を前に、リクエストごとに変わる内容を後ろに置く**ことです。
システムプロンプトの先頭に現在時刻を埋め込むだけで、以降のキャッシュがすべて無効になります。

また、explicit 方式では TTL の管理責任がアプリ側にも生じます。
「キャッシュがあるはず」を前提にした実装は、TTL 切れのタイミングで挙動が変わります。
なければ作ってから使う、というようにアプリ側でもキャッシュの存在を保証する設計にします。

# 4. リクエストオプション — デフォルトのまま叩かない

API リクエストのオプションは、デフォルトのままだと本番で困るものがいくつかあります。
代表的な例が下記です。

| オプション | デフォルトのまま叩くと | 推奨 |
|---|---|---|
| ロール(system / user) | ユーザー由来テキストを system に混ぜると、プロンプトインジェクションの入口になる | 指示は system、ユーザー由来テキストは user に隔離 |
| structured output | 出力の JSON パース失敗をアプリ側で処理し続けることになる | スキーマ指定で書式を API 側に保証させる |
| 安全フィルタ | ドメイン特有の語彙が誤ってブロックされることがある | 自ドメインの入力で挙動を確認し、明示設定する |
| temperature | 判定タスクでも出力が揺れる | 判定タスクは決定性寄りに設定(ただし後述の通り保証はない) |
| タイムアウト | SDK のデフォルト(10分程度)が長すぎて、ジョブ側のタイムアウトと不整合を起こす | 呼び出し側の想定に合わせて明示設定 |

いくつか補足します。

**ロール分離**は、どのプロバイダでも基本のインジェクション対策として位置づけられています。
OpenAI は Model Spec で命令の優先順位(Platform > Developer > User)を定義してモデルを訓練しており、Anthropic もロール定義とユーザー入力の分離を公式に推奨しています。
判定対象のテキストのような「外部の人間が書いたテキスト」を扱うなら、正規表現でのサニタイズよりも先に、まずロールを分けます。

https://openai.com/index/the-instruction-hierarchy/

**structured output** は3社とも提供していますが、制約が違います。
OpenAI は再帰スキーマに対応する一方で、数値の範囲制約が使えません。
Anthropic は再帰非対応です。
Gemini は `propertyOrdering` を明示しないと出力順が安定せず、複雑なスキーマは 400 エラーになります。
スキーマ設計の前に制約一覧を確認してください。

https://developers.openai.com/api/docs/guides/structured-outputs

https://platform.claude.com/docs/en/build-with-claude/structured-outputs

https://ai.google.dev/gemini-api/docs/structured-output

**安全フィルタ**は、仕組み自体が3社で違います。
Gemini はリクエスト単位で閾値を調整できます。
OpenAI は生成 API と分離した無料の moderation API を提供しています。
Anthropic は閾値設定を持たず、拒否時に `stop_reason: "refusal"` を返す方式です。
医療・介護ドメインのテキストには「注射」「入浴介助」「精神科」のような語が普通に登場し、Gemini のデフォルト設定では誤ブロックの可能性があります。
そのため私たちは safety settings を明示的にオフにしました。
医療系での誤発動は、公式フォーラムでも報告されています。
フィルタを切る場合は、ロール分離や出力の検証といった、代わりの安全策を持っているのが前提です。

https://ai.google.dev/gemini-api/docs/safety-settings

https://discuss.ai.google.dev/t/issue-with-gemini-safety-settings-in-medical-applications/2417

**決定性**は、どの社も保証していません。
OpenAI と Gemini には `seed` パラメータがありますが best-effort ですし、Anthropic に至っては新しいモデルで temperature パラメータ自体が廃止されました。
「同じ入力なら同じ出力」を前提にした設計はできない、というのが次章・次々章の前提になります。

# 5. エラー対応 — 429 と「200 なのに失敗」に備える

LLM API のエラーは、リトライで直るものと直らないものを分けて設計します。

| エラー | 意味 | リトライ |
|---|---|---|
| 429 | レート制限超過 | する(バックオフ付き) |
| 500 / 503 / 529 | プロバイダ側の障害・過負荷 | する(バックオフ付き) |
| 400 / 403 | リクエスト不正・権限不足 | しない(直して再送) |
| タイムアウト | 応答が返らない | 冪等なら再送 |
| 200 だが空応答・拒否 | 安全フィルタ等による拒否 | しない(後述) |

## レート制限の考え方は3社3様

429 対策の前に、レート制限の単位を知る必要があります。
ここもプロバイダごとに思想が違います。

- OpenAI はリクエスト数/分とトークン数/分の複数軸。上限は累積課金額に応じて自動昇格します
- Anthropic は入力トークンと出力トークンが別々の上限を持ち、入力だけ・出力だけでも 429 になりえます。自動昇格に加えて、引き上げ申請・個別交渉の窓口があります。キャッシュ読出しは入力側に計上されないため、キャッシュが実効スループットの向上にも効きます
- Vertex AI の新しめのモデルは Dynamic Shared Quota(DSQ)で、固定クォータも引き上げ申請も存在しません。429 は「自分の上限超過」ではなく「共有リソースプールの瞬間的な混雑」を意味します

https://developers.openai.com/api/docs/guides/rate-limits

https://platform.claude.com/docs/en/api/rate-limits

https://cloud.google.com/vertex-ai/generative-ai/docs/resources/dynamic-shared-quota

とくに DSQ の 429 は誤解しやすいポイントです。
自分のリクエスト数を数えていても防げず、プール側の混雑で発生します。
global エンドポイントを使うと、複数リージョンの容量に分散されて頻度が下がります。

https://cloud.google.com/blog/products/ai-machine-learning/reduce-429-errors-on-vertex-ai

対策の定石は次の3点です。

- **並列数をクライアント側で制御する**。1件の処理で複数プロンプトを並列発行する設計だと、「処理の同時多発 × プロンプト並列」の掛け算でリクエストが瞬間的に集中します。並列の上限は自分で持ちます
- **429/5xx はジッター付き指数バックオフでリトライする**。`retry-after` ヘッダが返ってきたらそれに従います。Anthropic は「それより早いリトライは失敗する」と明記しています。固定間隔の即時リトライは、混雑をさらに悪化させるアンチパターンです
- **リアルタイム性が不要な処理は Batch API に逃がす**。3社とも50%割引で、同期 API とは別のクォータ枠なので、レート制限そのものを回避できます

https://platform.claude.com/docs/en/build-with-claude/batch-processing

https://developers.openai.com/api/docs/guides/batch

https://ai.google.dev/gemini-api/docs/batch-api

## 200 なのに失敗、に備える

HTTP ステータスだけ見ていると、すり抜ける失敗があります。
4章で見た安全フィルタの拒否がその代表例で、3社とも 200 の正常応答の中に入って返ってくるからです。
Anthropic は `stop_reason: "refusal"`、OpenAI は structured output の `refusal` フィールドで返します。
Gemini は2パターンあり、入力段階でブロックされると candidates 自体が空になり、生成段階でブロックされると content が空で `finishReason: SAFETY` になります。
これらはリトライで直らないので、リトライ対象から外し、明示的に検出してフォールバックに回します。

https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons

https://docs.cloud.google.com/gemini-enterprise-agent-platform/reference/rest/v1/GenerateContentResponse

## フォールバック先を最初に決める

リトライしても直らないとき、ユーザー体験をどう守るかは実装前に決めておきます。
私たちは「LLM の判定がエラーになったら、従来どおり人手で判断するフローに静かに戻す」と決めていました。
ユーザーから見ると「結果がすぐに反映されなかった」だけで、エラー画面は見せません。
LLM を「失敗したら人間に返す高速化レイヤー」と位置づけると、この設計は自然に出てきます。

もう1つ、非同期処理特有の罠として「エラーにすらならず、進行中のまま止まる」ケースがあります。
処理状態を管理するテーブルを持つなら、タイムアウトで状態をリセットする後始末までを設計に含めます。

実際、私たちはモデル更新後に 429 が頻発したことがありますが、並列上限の導入とリトライの整備で収束しました。
フォールバックが決まっていたおかげで、この間もユーザー影響はありませんでした。

# 6. 評価とリリース — 正解のない出力をどう検証するか

最後は「作った機能をどう評価してリリースするか」です。
テストを書く前に必要なのは、「何をもって良い出力とするか」の定義です。

## 精度は適合率・再現率で語る

精度・コスト・レイテンシの3つは同時には取れないので、優先順位を決めます。
このとき出発点にすべきなのは、ベンチマークスコアの比較ではなく「どちらに間違えると致命的か」の定義です。

true / false の判定のような二値タスクの間違い方は、見逃しと誤検知の2種類です。
それぞれに対応する指標があります。

- **再現率(recall)** は、実際に該当するもののうち「該当」と判定できた割合。低いほど見逃しが多い
- **適合率(precision)** は、「該当」と判定したもののうち実際に該当していた割合。低いほど誤検知が多い

2つはトレードオフの関係にあり、どちらを優先するかはタスクの性質で決まります。
不正検知のように、見逃しが事故に直結し、誤検知は人手の再確認で救済できるタスクなら、再現率を優先して適合率は下流で補います。
逆に、正常なものを弾く誤検知がそのままユーザーの不利益になるタスクなら、適合率を優先します。
この定義があってはじめて、モデルの比較検証で見るべき数字が決まります。

注意したいのは、単純な「一致率」は当てにならないことです。
項目別の一致率が高くても、項目を束ねた最終判定では乖離が拡大します。
束ねる項目が多いほど、どれか1つの不一致で全体の判定が変わるからです。
また正例が少ないデータでは、一致率が高いのに再現率が壊れていることもあります。

## 性質と関係をテストする

LLM 機能のテストには固有の難しさがあります。
出力の期待値は事前に定義できません。そもそも正解を列挙できるなら、LLM は要らないからです。
しかも前述のとおり、出力は非決定的です。
テスト分野ではオラクル問題と呼ばれる状況で、通常の「入力 X なら出力 Y になるはず」という assert が書けません。

この状況で使えるテスト手法が知られています。

- **Property-based Testing** は、個別の正解ではなく「すべての出力が満たすべき性質」を検証します。true / false の判定機能なら「出力は必ず true か false のどちらか」「false なら理由が必ず付く」。前述の structured output と組み合わせると、性質の多くを API 側で保証できます
- **Metamorphic Testing** は、入力を変えたときに出力がどう変わる「べき」かの関係を検証します。判定機能なら「固有名詞のような無関係な箇所を変えても判定は変わらない」「条件に反する表現を追加したら、判定は false 側にしか動かない」。とくに後者のような方向つきの関係は、前節で定義した「間違いの非対称性」をそのままテストにできます

オラクル問題と各手法については、こちらの記事が参考になります。

https://zenn.dev/hacobell_dev/articles/48672302988d40

## シャドー実行から段階リリースへ

そして最終検証は本番トラフィックで行います。
段階は3つです。

1. **シャドー実行**。本番の入力で LLM を動かし、結果は使わず蓄積だけする。既存の人手フローの結果と突き合わせられるので、前述の適合率・再現率をここで実測できます
2. **少量リリース**。対象の数%だけ結果を実際に使い、計測する
3. **段階拡大**。数字を確認しながら比率を上げる

私たちもシャドー実行で既存フローとの比較を行い、ズレる箇所を特定・修正してから、1% → 段階拡大の順で本番適用しました。

## 検証レーンとして常設する

シャドー実行の仕組みは、リリースが終わったら畳むのではなく「検証レーン」として常設しておくことをおすすめします。
2章で見たとおりモデルには EOL があり、切替のたびにゼロから検証環境を組み直すことになるからです。
本番と同じ入力を別モデルでも処理して結果だけ蓄積するレーンがあれば、切替の検証がすぐ回せます。
この領域には golden dataset や LLM regression testing、offline eval といった確立した用語と手法があります。
golden dataset は人手レビュー済みの評価用データセット、LLM regression testing はモデルやプロンプトを変えるたびに固定データで再実行して基準と比較する手法です。
これらの用語で検索すると、設計の参考になります。

私たちもこの検証レーンで下位モデルを検証しました。
本番モデルとの乖離がすべて、再現率の落ちない「厳しい側」だったため、安心して採用できました。

# さいごに

全体をチェックリストにまとめます。

- プラットフォーム
    - 社内の既存経路に乗れるか
    - 使いたい機能はその経路で提供されているか
- モデル
    - 上位モデルで基準を作ってから下位を検証する順序になっているか
    - preview モデルを本番に据えていないか
- コスト
    - LLM でなくていい処理を混ぜていないか
    - キャッシュの前方一致を意識したプロンプト配置か
    - 使わない出力を生成させていないか
- オプション
    - ロール分離・structured output・安全フィルタ・タイムアウトをデフォルトのまま叩いていないか
- エラー
    - 429/5xx のバックオフと並列制御はあるか
    - 「200 なのに失敗」を検出しているか
    - フォールバック先は決めたか
- 評価
    - どちらに間違えると致命的かを、適合率・再現率で先に定義したか
    - 出力の性質と入出力の関係をテストしているか
    - シャドー実行で実測してから段階リリースしたか
    - 検証レーンは常設したか

こうして見ると、LLM API の扱いは外部 API 連携の一般論とほとんど同じです。
特徴的なのは、レスポンスが非決定的で、課金が従量で、モデルが向こうの都合で入れ替わっていくことです。
検証レーン・コスト設計・段階リリースという3点の備えさえ仕組みにしておけば、LLM は特別扱いの要らない通常の部品として運用できます。
この記事が、これから LLM を本番に組み込む方のサポートになれば幸いです。
